# WakeUp — 버스 하차 알림 개발 계획

## 0. 결정 사항 요약
| 항목 | 결정 | 이유 |
|---|---|---|
| 형태 | iPhone 홈 화면 웹앱(PWA) + 개인 서버 | Mac 없음, App Store 미출시, 나만 사용 |
| 위치 판정 | **내가 탄 버스의 GPS**(공공 버스위치 API) | 웹은 백그라운드 GPS 불가. 폰 배터리 소모 없음 |
| 알림 | Web Push (iOS 16.4+, 홈 화면 앱) | 잠금화면 알림 가능 |
| 서버 | 내 노트북 상시 실행 + Tailscale Funnel | 무료, 외부(LTE) HTTPS 접속 |
| 지역 | 서울·경기(성남) 우선, 전국 지원 | 서울시 / 경기도 / TAGO 3개 공급자 |
| 효율 | 트립 중에만 조회, 도착 시 자동 중단. 노선 데이터는 트립 시작 시 캐시가 3일 넘었을 때만 갱신 | 불필요한 호출 제거 |
| 첫 단계 | **버스위치 API 정확도·지연 실측** 후 본 개발 | 공식 갱신주기 미공개 |

## 1. 목표
- 시내버스 탑승 중 **목적지 1~2정거장 전**에 iPhone 잠금화면 푸시 알림.
- 시간 기반이 아닌 GPS 기반 판정.
- 폰은 백그라운드 위치 수집 없음. 서버의 버스 위치 조회도 트립 중에만, 도착 시 자동 중단.

## 2. 구성
```
[iPhone: 홈 화면 웹앱(PWA)]
   │ HTTPS (Tailscale Funnel)
   ▼
[노트북 서버: Node.js]
   ├─ 공급자 어댑터 ──► 서울시 / 경기도 / TAGO API (노선·정류장·버스위치)
   ├─ SQLite (노선 캐시, 트립, 즐겨찾기, 푸시 구독)
   └─ Web Push 발송 ──► Apple 푸시 서버 ──► iPhone 잠금화면
```

| 항목 | 선택 |
|---|---|
| 클라이언트 | PWA (TypeScript, Vite) |
| 서버 | Node.js + TypeScript, Fastify |
| 저장 | SQLite (better-sqlite3) |
| 푸시 | Web Push (VAPID, `web-push`) |
| 외부 접속 | Tailscale Funnel (고정 HTTPS 주소, 무료) |
| 프로세스 관리 | pm2 (자동 재시작, 부팅 시 자동 실행) |

## 3. 사용자 흐름
1. (최초 1회) Safari로 접속 → 공유 > **홈 화면에 추가** → 홈 화면 앱에서 알림 허용, 비밀 토큰 입력.
2. 노선 검색 → 탑승·목적지 정류장 선택 (또는 즐겨찾기) → 알림 시점 1/2정거장 전 선택.
3. 버스에 탄 뒤 **"탑승했어요"** → 폰 GPS 1회 측정 → 서버가 탑승 차량 식별 → "추적 시작" 푸시.
4. 앱을 닫아도 됨. 서버가 차량 위치 추적.
5. 목적지 N정거장 전 → 하차 알림 푸시. 목적지 도달 → 추적 종료.

## 4. 데이터 소스
지역별 버스정보시스템이 달라 **3개 공급자 어댑터**를 둔다. 세 곳 모두 각 버스 GPS 단말기 → 지자체 교통정보센터(서울 TOPIS, 경기 GBIS 등) 데이터로, 정류장 전광판·서울버스/경기버스 앱과 같은 원천이다.

| 공급자 | 담당 |
|---|---|
| 서울시 버스정보 API (서울 열린데이터광장) | 서울시 면허 노선 |
| 경기도 버스정보 GBIS (공공데이터포털) | 경기도 면허 노선 (성남 포함 31개 시군, 경기 광역버스) |
| 국토교통부 TAGO (공공데이터포털) | 그 외 전국 (인천·광역시·지방 도시) |

```ts
interface BusProvider {
  searchRoutes(query: string): Promise<Route[]>;
  getRouteStops(routeId: string): Promise<Stop[]>;   // id, order, name, lat, lng
  getVehicles(routeId: string): Promise<Vehicle[]>;  // vehicleNo, stopOrder, lat, lng, updatedAt
}
```
- **공급자는 노선의 면허 지자체 기준**으로 결정 (버스 현재 위치 기준 아님). 서울↔성남 노선도 공급자 하나로 전 구간 추적.
- 노선 검색은 세 공급자에 동시 질의 후 병합. 중복 노선은 면허 지자체 쪽만 사용.
- 노선번호 + 기점·종점 + 지역을 함께 표시해 동명 노선 구분.
- API 키는 공급자별 개별 신청, 서버 `.env`에만 저장 (git 제외).

### 4.1 노선/정류장 데이터 갱신
- 즐겨찾기·트립은 순번이 아닌 **정류장 ID + 노선 ID**로 참조. 순번·좌표는 최신 목록에서 재계산.
- **트립 시작 시 1회**, 캐시가 3일 넘은 경우에만 해당 노선 조회 (API 1회). 트립은 캐시로 즉시 시작, 조회는 병렬. 실패 시 캐시 사용.
- 정류장 ID가 사라지면 같은 이름 또는 200m 이내 정류장으로 자동 매칭 후 1회 확인 요청. 후보 없으면 "확인 필요" 표시.
- 응답 검증(정류장 0개, 좌표 이상, 순번 누락) 실패 시 기존 캐시 유지.

## 5. 탑승 차량 식별
1. "탑승했어요" 시 폰 GPS 1회 측정 (앱이 화면에 떠 있으므로 가능, 정확도 100m 이하까지 최대 10초).
2. 해당 노선 운행 차량 중 폰 위치와 가장 가까운 차량 선택 (거리 ≤ 300m, 정류장 순번이 탑승 정류장 ±1).
3. 후보가 2대 이상이거나 없으면 차량번호 목록 표시 → 사용자 선택 (차량번호는 버스 내부 표시).
4. 30초 후 재조회해 목적지 방향 진행 확인. 아니면 재선택 푸시.

## 6. 추적 및 알림 판정 (서버)
- 트립별 상태머신: `Identifying → Tracking → Alerted → Done`
- 남은 정류장 수에 따라 조회 간격 조절:

| 목적지까지 남은 정류장 | 조회 간격 |
|---|---|
| > N + 5 | 60초 |
| N + 1 ~ N + 5 | 20초 |
| ≤ N (알림 후) | 20초 (도착 감지) |

- **알림 조건** (하나라도 만족 시 1회 푸시):
  1. 차량 정류장 순번 ≥ 목적지 순번 − N
  2. 차량 좌표가 알림 정류장 반경 150m 이내
  3. **지연 보정 추정 위치**가 알림 정류장 도달 (아래)
- **지연 보정**: 차량 위치가 일정 시간(M1 실측값 기준) 갱신되지 않으면, 마지막 위치 + 최근 구간 평균 속도로 노선 위 현재 위치를 추정.
- 정류장 순번이 "직전 통과"인지 "다음 정류장"인지는 공급자별로 M1에서 확정.

## 7. 자동 종료 (조회 중단)
- 차량 정류장 순번 ≥ 목적지 순번 (도착)
- 사용자가 알림 또는 앱에서 "종료"
- 차량이 3회 연속 목록에서 사라짐 → "추적 끊김" 푸시 후 종료
- 최대 3시간 경과

종료 시 폴링 타이머 해제. 진행 중 트립이 없으면 서버는 외부 API를 호출하지 않음.

## 8. 푸시 알림
- iOS 16.4 이상, **홈 화면에 추가한 웹앱에서만** 동작. 권한은 버튼 탭으로 요청.
- 구독 정보는 SQLite에 저장 (서버 재시작 후에도 유지). 만료(HTTP 404/410) 시 앱 실행 때 재구독.
- 내용: "다음 정류장 ○○ — 2정거장 뒤 하차". 탭하면 트립 화면.
- 트립 시작 시 "추적 시작" 푸시로 수신 여부 즉시 확인.

## 9. API 호출량
- 개발계정 한도: 공급자·기능별 일 1,000회 수준 (신청 시 확인).
- 30분 트립 ≈ 40~60회 → 하루 여러 번 타도 충분. 부족하면 운영계정 신청.

## 10. 노트북 서버 운영
| 항목 | 대응 |
|---|---|
| 밖에서(LTE) 접속 | Tailscale Funnel 고정 주소 `https://<기기명>.<tailnet>.ts.net` (PWA·푸시용 HTTPS 충족) |
| 덮개 닫음/절전 | 전원 연결 시 절전 끄기, 덮개 닫아도 동작 유지 |
| 재부팅/크래시 | pm2 자동 재시작 + 부팅 시 자동 실행 |
| 공개 주소 보안 | 1인용 비밀 토큰(쿠키 저장) 없으면 모든 API 거부 |
| 노트북 꺼짐 | 트립 시작 전 서버 상태 확인 → 응답 없으면 "서버 꺼짐" 표시 |
| 네트워크 끊김 | 외부 API 실패 시 재시도, 복구 후 즉시 상태 재계산 |

- OS 비의존 코드 (Windows/Linux). 필요 시 무료 클라우드 VM으로 코드 변경 없이 이전.

## 11. 디렉터리 구조
```
WakeUp/
├── server/
│   ├── src/
│   │   ├── api/          # HTTP 라우트 (노선 검색, 트립, 구독, 상태)
│   │   ├── providers/    # seoul/, gyeonggi/, tago/ (BusProvider 구현)
│   │   ├── trip/         # 상태머신, 판정·지연 보정 (순수 함수, 테스트 대상)
│   │   ├── scheduler/    # 트립별 폴링 타이머
│   │   ├── push/         # Web Push 발송
│   │   └── db/           # SQLite 스키마, 마이그레이션
│   └── test/fixtures/    # 실측 API 응답 기록
├── web/
│   ├── src/              # 화면: 검색, 즐겨찾기, 트립 진행
│   ├── public/manifest.webmanifest
│   └── sw.ts             # 서비스워커 (푸시 수신)
├── tools/recorder/       # M1 실측용 API 기록 스크립트
└── docs/
```
- 서버가 `web/` 빌드 결과를 함께 제공 → 주소 하나로 운영.

## 12. 마일스톤
| # | 범위 | 산출물 | 완료 기준 |
|---|---|---|---|
| M0 | 셋업 | 모노레포, TypeScript, lint/test, API 키 발급 (서울·경기·TAGO) | 키로 각 API 1회 호출 성공 |
| M1 | **실측 (진행 여부 판단)** | 기록 스크립트로 실제 탑승 중 API 응답 + 폰 GPS 동시 기록 | 공급자별 위치 지연·갱신 간격·순번 의미 확정, 기본 N 결정 |
| M2 | 판정 로직 | 상태머신, 지연 보정 + M1 기록 재생 테스트 | 기록된 트립 전부에서 알림 시점 정상 |
| M3 | 서버 | 공급자 어댑터 3종, 통합 검색, 트립 API, 스케줄러, 자동 종료, 노선 갱신 | 목 서버로 트립 전체 흐름 통과 |
| M4 | 웹앱 + 푸시 | PWA, 서비스워커, 구독, 차량 식별 UI, 즐겨찾기 | 잠금 상태 iPhone에서 푸시 수신 |
| M5 | 운영 | Tailscale Funnel, pm2, 토큰 인증, 서버 상태 표시 | LTE에서 접속·트립 성공 |
| M6 | 필드 테스트 | 서울·성남 실제 탑승, 간격·반경·N 튜닝 | 10회 탑승 알림 누락 0 |

- M1 결과 지연이 너무 커서 1~2정거장 전 알림이 불가능하면, 다른 방식(예: 탑승 시 폰 화면 켜둔 채 폰 GPS 병행) 재검토.

## 13. 테스트
- 단위: 판정 로직에 기록된 버스위치 시퀀스 주입 (정상, 정류장 건너뜀, 차량 사라짐, 갱신 지연, 버스 몰림).
- 통합: 공급자 목 서버로 트립 전체 흐름 재생.
- 실기기: iPhone 홈 화면 앱 잠금 상태 푸시 수신, 실제 탑승.
